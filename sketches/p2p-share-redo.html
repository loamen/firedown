Send directly — redo

The transport stays: WebRTC DataChannel in the hidden GeckoSession, the offline codes, the mailbox, the resume handshake. Two things change. The transfer gets a service, so the sender can leave the screen (today session lifetime = view lifetime: a 5 GB send means holding the phone on that screen). Nearby gets a device list: the receiver's phone shows up on the sender's screen by name, tap it, it asks the receiver, done — no QR, no camera, no reply code (the LocalSend / Quick Share / AirDrop shape). The QR and the link stay as the fallbacks for a phone on another network.

What the sketch keeps and what it drops

  • Keeps: the engine page, FDS1/FDR1/FDO1 codes, P2pAnswerServer (it becomes the thing the LAN discovers), the rendezvous mailbox for links, STUN, the relay footer rule, the resume handshake, the Accept-before-anything-connects preview.
  • Adds: an NSD advertisement while the Receive screen is open (_firedown._tcp, the answer server's port, the device name), NSD discovery on the Send screen, one new LAN endpoint (POST /offer) so the offer travels to the picked device directly, and a dataSync foreground service that owns the controller and the hidden session (the download engine's shape).
  • Drops from the common path: the reply stage, the "Nearby? Show the QR" fold, the paste/scan pair on both screens (they fold into one "Got a code?" row), and the sender-must-babysit rule.
  • Does not solve: a recipient without Firedown (that is the browser-recipient receive, a separate build), multi-file sends.

Current (1.2.01)

CURRENT — link first, QR folded, reply stage, sender holds the screen

Send: file card → "Send link" / "Private link" → waiting (paste reply, link again) → the nearby QR behind a fold. Receive: Scan or Paste → preview → Accept → (reply stage when no mailbox) → progress. Both ends must be on these screens the whole time.

Proposed

A — Nearby list first, link second, background transfer

The Send screen opens on a list of phones running Firedown's Receive screen on this Wi‑Fi (NSD). Tap one → its Receive screen shows the request → Accept → transfer, which continues from a foreground service with a notification; the screen is a window onto it, not its owner. "Anywhere" keeps the link (and the QR under it) for a phone that is not on this network.

B — Same, but the receiver is a SETTING, not a screen (Quick Share's model)

"Visible to nearby Firedown devices" in Settings → Downloads keeps the phone announced on every Wi‑Fi it joins; a request arrives as a notification with Accept, no screen to open first. Fewer taps for the receiver, but the phone broadcasts its name on every network it joins, for as long as the switch is on. Not the recommendation: A announces only while a screen the user opened is in front of them, which is the privacy posture this app sells. Recorded so it is not re-derived.
